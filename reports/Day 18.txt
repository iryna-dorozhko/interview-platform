ЗВІТ ЗА 28 ЛИПНЯ 2026
AI-платформа співбесід — decision letter: аргументація відмови та accept offer

================================================================================

НА СТАРТІ ДНЯ (EXECUTIVE)

1. Що отримав продукт сьогодні
   Decision letter тепер розрізняє HIRE і REJECT сценарії: при відмові агент
   обов'язково генерує аргументацію (чому кандидат не підходить), а при прийнятті —
   включає конкретні рядки offer вакансії (зарплата, умови) у лист.

2. Головний технічний результат
   Новий pipeline у decision-letter-agent: витяг vacancy offer lines →
   умовне збагачення промпту залежно від типу рішення → валідація наявності
   аргументації/offer у згенерованому листі.

3. Головний продуктовий результат
   HR більше не отримує generic «ми вирішили не продовжувати» — лист
   конкретний і обґрунтований. Кандидат при accept бачить реальну пропозицію,
   а не абстрактне «вітаємо».

4. Фактичний обсяг дня
   - 5 комітів.
   - ~772 доданих / ~3 видалених рядків.
   - Design spec + plan + реалізація + тести.

5. Що планується далі
   Перевірити генерацію листів на реальних кейсах із різними offer-блоками;
   переконатися, що аргументація відмови не є образливою чи занадто деталізованою.


================================================================================
КОРОТКИЙ ПІДСУМОК
================================================================================

День повністю присвячений одній фічі — покращенню якості decision letters.
Робота пройшла весь цикл: design → plan → implementation → tests.

Два основні блоки:

1. **Дизайн і планування** — design spec та plan для reject argumentation
   і accept offer у decision letters (613 рядків документації).
2. **Реалізація** — витяг offer lines із vacancy profile, збагачення промпту
   decision-letter-agent, валідація присутності аргументації/offer, передача
   vacancy offer через reports route.


################################################################################
# 1. ДИЗАЙН І ПЛАНУВАННЯ
################################################################################

================================================================================
ЩО ЗРОБЛЕНО
================================================================================

- Design spec: аналіз поточного стану, вимоги до аргументації reject і
  включення offer при accept, edge cases (vacancy без offer, partial offer).
- Implementation plan: покроковий план із чіткими acceptance criteria для
  кожного кроку, dependency graph між компонентами.

================================================================================
ЧОМУ ЦЕ ВАЖЛИВО
================================================================================

Формалізація вимог перед кодом дозволила одразу врахувати edge cases
(vacancy без offer lines, reject без достатніх даних для аргументації)
і уникнути переписування.


################################################################################
# 2. РЕАЛІЗАЦІЯ: DECISION LETTER AGENT
################################################################################

================================================================================
ЩО ЗРОБЛЕНО
================================================================================

1. EXTRACT VACANCY OFFER LINES
   - Нова функція у decision-letter-agent для витягу offer-рядків із vacancy.
   - Unit-тести на різні формати offer (повний, частковий, відсутній).

2. REQUIRE REJECT ARGUMENTATION AND ACCEPT OFFER
   - Промпт decision-letter-agent доповнено умовними інструкціями:
     REJECT → обов'язкова аргументація.
     HIRE/ACCEPT → обов'язкове включення offer lines.
   - Тести на валідацію згенерованого контенту.

3. PASS VACANCY OFFER INTO DRAFT
   - Reports route передає vacancy offer у decision letter draft endpoint.
   - Агент отримує повний контекст для генерації.

================================================================================
ЧОМУ ЦЕ ВАЖЛИВО
================================================================================

Раніше decision letter був «одного розміру для всіх» — однакова структура
незалежно від типу рішення. Тепер лист адаптований до контексту:
- Кандидат при відмові розуміє причини.
- Кандидат при прийнятті бачить конкретну пропозицію.
- HR не потрібно вручну дописувати ці блоки.


################################################################################
# СУМНІВИ / ВІДКРИТІ ПИТАННЯ
################################################################################

1. ЯКІСТЬ АРГУМЕНТАЦІЇ ВІДМОВИ
   Чи не генерує агент занадто деталізовану або потенційно образливу
   аргументацію? Потрібен review на реальних кейсах.

2. VACANCY БЕЗ OFFER
   Що робить агент, коли vacancy profile не містить offer lines?
   Fallback поведінка потребує перевірки на реальних даних.

3. TONE CALIBRATION
   Accept letter має бути ентузіастичним, reject — тактовним. Чи достатньо
   промпт-інструкцій для стабільного тону, чи потрібні few-shot examples?

4. LEGAL COMPLIANCE
   Чи немає ризику, що аргументація відмови містить дискримінаційні формулювання?
   Можливо потрібен додатковий safety layer.

2. Review тону reject листів — переконатися, що аргументація тактовна.
3. Перевірити fallback при відсутності offer lines у vacancy.
4. Розглянути додавання few-shot examples у промпт для стабілізації якості.
5. Інтегрувати з UI: HR має бачити preview листа перед відправкою.


================================================================================
РЕФЛЕКСІЯ
================================================================================

Що сьогодні було найважливішим?

  Повний цикл від дизайну до тестів для однієї чітко обмеженої фічі.
  Менший обсяг коду, але вищий вплив на якість продукту для кінцевого
  користувача (кандидата).

Який головний продуктовий висновок?

  Decision letter — це перша (і часто єдина) комунікація після співбесіди.
  Якість цього листа прямо впливає на враження кандидата від платформи.
  Інвестиція в контекстну генерацію виправдана.

Що зараз обмежує продукт?

  Немає реальних даних про те, як виглядають згенеровані листи на
  різноманітних вакансіях. Потрібна калібрувальна сесія.

Що варто пам'ятати далі?

  Фічі, що впливають на tone-of-voice продукту, потребують більше QA
  на реальних даних, ніж типові CRUD-операції. Наступний крок — не нова
  фіча, а верифікація якості на реальних сценаріях.
